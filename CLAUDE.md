# CLAUDE.md

Guidance for Claude Code in this repo.

## Project

**Hagenton** — simulatore retrospettivo di risparmio/investimento per l'Hagenthon
(Accenture), tema **02 · Inclusione Finanziaria**. Mostra quanto si sarebbe
accumulato investendo in passato in uno strumento a scelta (azionario,
obbligazionario, bitcoin, libretto postale, conto fermo), con inflazione e
tassazione opzionali. Obiettivo educativo: far capire il costo-opportunità del
non risparmiare, **non** dare consigli di investimento.

- **Stack**: Next.js (App Router) + React + TypeScript, Tailwind CSS
- **Persistenza**: `localStorage` — nessun backend, nessun database, nessuna auth
- **Nessuna chiamata di rete a runtime**: dati finanziari solo da dataset statici
  bundlati nel repo

## Vincolo non negoziabile del tema hackathon

**Mai raccomandazioni di investimento, consulenza personalizzata, o indicazioni su
cosa comprare/vendere/scegliere** — in nessun testo, label, messaggio di errore o
commento. Il framing è sempre retrospettivo/illustrativo ("ecco cosa sarebbe
successo con questi dati storici"), mai prescrittivo ("dovresti fare così"). Questo
vale per ogni riga di UI copy, non solo per la logica di calcolo. Vedi già
`apps/web/app/faq/page.tsx` per il tono corretto ("è un cambio di prospettiva, non
uno strumento di investimento").

## Assistant Behavior

- **No "Generated by" comments**: nessuna attribuzione nel codice.
- **Minimal chat output**: conciso, codice più che prosa.
- **Lingua**: codice, identificatori, commenti → **inglese**. Copy rivolto
  all'utente (label, messaggi, contenuti educativi in UI) → **italiano** (pubblico
  target dell'hackathon). Documentazione di repo (README, questo file) → italiano.
- **Clean code**: rimuovere codice morto, import inutilizzati, file obsoleti quando
  si refactora/sposta qualcosa. Nessun artefatto orfano.
- **Dark/light mode**: già implementato (`components/ThemeToggle.tsx`,
  `lib/theme.ts`). Ogni componente nuovo usa i token CSS in
  `apps/web/app/globals.css`/`tailwind.config.ts`, mai colori hardcoded, per
  restare compatibile con entrambi i temi — verificato da `ui-guardian`.

## Elementi vietati / alternativa

| Vietato | Usa invece |
|---|---|
| `fetch`/chiamate API esterne a runtime per dati finanziari | dataset statico in `lib/data/` |
| `any` sui dataset caricati | guard/validazione tipizzata a runtime |
| eccezione non gestita raggiungibile da input utente | risultato o errore strutturato |
| stringa libera per la chiave di uno strumento | union type / `as const` condivisa tra dataset, costanti e select |
| linguaggio prescrittivo ("dovresti", "conviene", "ti consigliamo") in UI copy | linguaggio retrospettivo/illustrativo |
| colore/spaziatura/font hardcoded | token da `globals.css`/`tailwind.config.ts` |

## UX/UI Guidelines

- **CTA standard**: disabilitato finché il form non è valido, validazione inline
  sui singoli campi.
- Ogni interazione utente deve portare a uno stato valido: mai una pagina bianca o
  un crash React per una combinazione di input, anche assurda.
- Palette, token, accessibilità (contrasto AA, focus, touch target ≥44px): vedi
  `apps/web/DESIGN_SYSTEM.md`, verificato da `ui-guardian` su ogni modifica visiva.

### Design system — regole chiave (dettaglio completo in `DESIGN_SYSTEM.md`)

- **Il giallo (`accent`) è solo fill**, mai testo: contrasto insufficiente su
  crema/bianco. Testo di enfasi (numeri) usa `accent-strong`, **solo se
  grande/bold** (≥18.66px bold).
- **Una sola azione primaria per vista** (`bg-primary` + `text-primary-foreground`,
  forma pill).
- **Numeri finanziari sempre `tabular-nums`.**
- Nessun colore/raggio/spaziatura hard-coded: solo token da `globals.css`/
  `tailwind.config.ts`.

### Dark mode — come funziona (non romperlo)

- Tema applicato via `data-theme="dark"|"light"` su `<html>`, letto dai token CSS
  in `:root[data-theme="dark"]` (`globals.css`).
- Uno **script inline in `<head>`** (`THEME_INIT_SCRIPT` in `lib/theme.ts`) imposta
  l'attributo **prima dell'idratazione** per evitare il flash del tema sbagliato —
  deve restare il primo elemento in `<head>` (`layout.tsx`), non spostarlo né
  renderlo un componente React lato client.
- Persistenza in `localStorage` (chiave `hagenton:theme:v1`), fallback a
  `prefers-color-scheme` se non impostato.
- `ThemeToggle` legge il tema reale solo dopo il mount per non divergere dall'HTML
  SSR (pattern da riusare per qualsiasi altro stato letto da `localStorage`/`window`).

### Pattern di accessibilità già in uso (da riutilizzare, non reinventare)

- Touch target interattivi: `min-h-11`/`min-w-11` (44px).
- Voce di navigazione attiva: `aria-current="page"`.
- Menu/disclosure: `aria-expanded` + `aria-controls` sul trigger.
- Toggle booleani (es. tema): `role="switch"` + `aria-checked`, mai una checkbox
  nascosta senza semantica.
- Icone/elementi decorativi: `aria-hidden="true"`; azioni solo-icona: `aria-label`.

### Convenzione chiavi `localStorage`

Formato `hagenton:<dominio>:v<n>` (es. `hagenton:scenarios:v1`,
`hagenton:theme:v1`). Il numero di versione va incrementato quando cambia la shape
dei dati salvati; il codice che legge deve restare tollerante a dati salvati con
una versione precedente (vedi il vincolo del `finance-engine` su scenari che
referenziano uno strumento non più esistente).

## Error Handling

Stato/risultato strutturato, mai eccezioni che risalgono fino alla UI per errori
prevedibili (input fuori range, dataset incompleto per il periodo scelto). Vedi
`.claude/agents/finance-engine.md` per le regole specifiche del motore di calcolo.

## Agenti specializzati

Ogni agente ha una definizione operativa in `.claude/agents/<nome>.md` (invocabile
da Claude Code) e una scheda di governance leggibile in `agents/<nome>/README.md`
(convenzione descritta in `agents/README.md`).

- **`finance-engine`** — tutto ciò che tocca `lib/finance.ts`, `lib/constants.ts`,
  `lib/data/**`: regole rigide su cosa può/non può fare, checklist "a prova di
  utente", fuzz test obbligatorio.
- **`ui-guardian`** — guardiano del design system: va invocato prima di finalizzare
  qualsiasi modifica visiva (componenti, token, nuove pagine).
- **`code-reviewer`** — gatekeeper obbligatorio prima di ogni `git push`: type-check,
  lint, build. Se trova errori non pusha e chiede come procedere.
- **`accessibility-auditor`** — audit di accessibilità WCAG 2.2 (A + AA) di pagine e
  componenti: produce un report Excel in `reports/accessibility/` e chiede se
  correggere i problemi (non applica fix senza autorizzazione).

## Deliverable richiesti dal tema (da tenere a mente durante lo sviluppo)

1. **User Difficulty Statement** — chi è l'utente, quale difficoltà ha nel capire
   il costo del non risparmiare/investire.
2. **Before/After Simplicity Evidence** — un caso concreto reso comprensibile
   dalla simulazione (schermata prima/dopo).
3. **Risk & Clarity Note** — cosa è stato semplificato (dataset, tassazione), cosa
   non è stato alterato, come si evita l'ambiguità con un consiglio di investimento.

## Testing

Nessun test runner ancora configurato in `apps/web`. Il subagent finance-engine è
responsabile di introdurre `vitest` per `lib/*` quando tocca quella logica —
non è opzionale per il motore di calcolo, lo è per il resto del repo durante
l'hackathon (5 ore, 2 persone: priorità a correttezza del motore, non a coverage
totale).
